# DATA-005: synthetic batch coordination (repository-only)

`job_cost.batch.run_batch(items, checkpoint, limit=None)` consumes an ordered, stable tuple of invented `SyntheticItem`s. It delegates each new item to the existing `adapters.process_item` boundary; it neither reads workbook files nor recomputes source facts. `BatchProgress` contains aggregate total/completed/handled/needs_review/failed/pending counts and ordered `ItemStatus` records with source ID, original-byte SHA-256, terminal state and stable reason code. It does not contain documents, raw cells, formulas or exception text. Treat source IDs and hashes as private runtime metadata when used with real sources; do not publish live progress or checkpoint records in this repository. An invalid identity has no echoed ID/hash, no checkpoint and a safe `invalid_identity` status; it does not block the rest of the manifest.

The caller must supply a truthful original-byte digest and a stable manifest; this layer does not compute/verify hashes or inspect files. Within one manifest, duplicate source IDs (even with differing hashes) fail before writes. The key is `(source_id, sha256, pipeline_version)`; `PIPELINE_VERSION` must change when parser, classifier, adapter registry, schema or coordination semantics change. Reusing a source ID with a different digest or revision is a distinct processing record. `limit` bounds *new* attempts per invocation (not already recorded results); pending items stay pending. Every handled, review or failed item is terminal for that revision. Replaying the same manifest against the same checkpoint reads results rather than adapting again. Retrying a terminal failure requires a new pipeline revision or an explicitly governed reset. Unknown shapes still need review, never a guessed adapter; failed/review records have no imported document.

`BatchCheckpoint` defines `get(key)` and `put_if_absent(key, result) -> stored_result`. Implementations must atomically commit the complete item result and checkpoint under the same key (or provide an atomic equivalent), return the existing record if already present, and preserve immutable source identity. Results must not be published as durable independently of their checkpoint. A resumed run must see the same records; a mismatched/corrupt record fails closed. `MemoryCheckpoint` is only a single-process, single-writer example: state disappears when the process exits. Reuse the *same instance* to simulate interruption/resume in tests. A real runtime must provide a governed transactional store, durable manifest, access controls, serialization/versioning, single-writer or atomic concurrency, and secure error/log handling. No such persistence, migration, external side effect or deployed runtime is included here.

Synthetic tests cover 375 items, bounded resumption, replay without duplicate adaptation, malformed isolation, unknown-shape review, safe progress and retained source/document identity. A trusted workflow may run `python -m unittest discover -s tests`; this document does not claim that tests have run, real 350+ corpus coverage, governed-storage persistence, representative reconciliation, staging deployment or Hedy acceptance. Rollback: revert the DATA-005 change (`job_cost/batch.py`, `tests/test_job_cost_batch.py`, this document); no migration or runtime mutation is involved.
